# 面试讲稿：工业设备预测性维护平台

## 90 秒项目介绍

这是一个面向工业互联网岗位的端到端作品集项目。我使用 UCI AI4I 2020 公开合成数据，目标不是声称做过真实工厂落地，而是展示从数据治理、模型评估到服务部署的完整能力。

数据只有 3.39% 故障样本，因此我先建立 Logistic Regression 基线，再训练类别平衡 Random Forest。主模型在独立测试集取得 PR-AUC 0.7476、Recall 0.7451、Precision 0.6032、F1 0.6667。我只在验证集上选择 0.335 阈值，测试集保留到最后一次评估，避免通过反复调参污染测试结果。随后用 SHAP 和逐条假阳性、假阴性分析解释模型行为。

工程侧使用 FastAPI 提供单条、批量预测、health 和 metrics，PostgreSQL 保存预测与告警记录，React/Vite 展示工业监控看板；Docker Compose 负责本地编排，pytest 和 GitHub Actions 做 API 与模型回归验证，最终部署到 Render。所有高风险动作都只给出告警和人工确认，不实现自动停机。

## 1. 如何防止数据泄漏？

我的处理分三层：

1. `UDI` 和 `Product ID` 是身份标识，可能让模型记忆样本而不是学习工况，因此排除。
2. `TWF/HDF/PWF/OSF/RNF` 是故障发生后的模式标签，与目标高度同源，作为输入相当于提前告诉模型答案，因此排除。
3. 先固定分层 train/validation/test，再只用 validation 选择阈值；test 不参与模型或阈值决策。

如果进入真实工厂，我还会按设备和时间切分，避免同一设备相邻时间窗口同时出现在训练与测试中。

## 2. 为什么优先看 Recall 和 PR-AUC？

故障率只有 3.39%，Accuracy 会被大量正常样本主导；即使全部预测正常也能得到很高准确率，但没有业务价值。

- Recall 回答“真实故障中识别出了多少”，直接对应漏报风险。
- Precision 回答“触发的告警中有多少是真的”，对应检修资源和告警疲劳。
- PR-AUC 汇总不同阈值下 Precision–Recall 权衡，对稀有正类比 ROC-AUC 更有辨识力。

我不会只追 Recall，因为无限降低阈值会制造大量误报。最终仍要结合检修成本、安全等级和人员容量选择工作点。

## 3. 阈值 0.335 是怎么选的？

训练完成后，我在验证集枚举 181 个候选阈值，选择 F1 最大的 `0.335`。这样同时约束 Recall 与 Precision，又不触碰测试集。该阈值在测试集得到 Recall 0.7451、Precision 0.6032、F1 0.6667。

这不是“工业最优阈值”。真实部署应定义成本函数，例如漏报一次关键设备故障的代价远高于一次人工复核，则阈值可能需要降低；如果检修资源有限，则要提高 Precision 或按设备重要度设置不同阈值。

## 4. 如何解释误报和漏报成本？

测试集混淆矩阵是 TN=1,424、FP=25、FN=13、TP=38。

- 13 个 FN 是漏报，可能造成设备损坏、非计划停机或安全风险，是工业场景更需要关注的错误。
- 25 个 FP 是误报，会消耗检查工时、备件和计划窗口，也可能导致告警疲劳。
- 当前漏报率为 25.49%，说明模型可用于展示风险筛查流程，但不能宣称满足真实安全关键生产要求。

下一步会按设备关键度、维护成本和安全后果建立分层成本矩阵，并做概率校准与按时间滚动验证。

## 5. 为什么不实现自动停机？

模型来自合成静态数据，没有真实设备校准、冗余传感器验证、功能安全认证或现场联锁测试。自动停机会直接影响人员安全、设备寿命和生产连续性，不能由演示级模型单点触发。

因此平台只输出概率、阈值和告警建议，并明确要求人工确认。真实系统中，模型更适合作为维护决策支持信号，由规则、PLC/SIS 联锁、操作规程和授权人员共同决定动作。

## 6. 为什么选择 Random Forest？

AI4I 是表格型数据，样本规模只有 10,000，Random Forest 能建模非线性与变量交互，对缩放不敏感，并能配合类别权重和 SHAP 解释。Logistic Regression 保留为透明基线，证明复杂模型确实带来了 PR-AUC 与 Recall 提升。若继续迭代，我会比较 XGBoost/LightGBM、概率校准和按设备时间序列模型，但不会只因模型更复杂就替换当前方案。

## 7. SHAP 告诉了什么？

在 1,000 条样本上，平均绝对 SHAP 最高的是扭矩、转速和工具磨损。这说明模型主要依赖可理解的运行工况，而不是身份字段。SHAP 解释的是模型如何形成预测，不证明变量对故障有因果作用；真实工厂仍需结合机理、传感器质量和工程师经验验证。

## 8. 生产化还缺什么？

当前版本是可部署演示，不是生产系统。主要差距包括：真实时序数据与跨设备验证、漂移监控、概率校准、认证授权、速率限制、审计日志、数据库迁移、消息队列、可观测性、备份恢复、HA，以及正式的网络安全和功能安全评审。

- 现场如何定义漏报与误报成本，阈值由算法团队还是设备专家共同标定？
- 数据切分是否需要按产线、设备型号和时间做跨域验证？
- 模型告警如何进入现有 MES、EAM 或点检工单流程，并保留人工确认和审计链路？
